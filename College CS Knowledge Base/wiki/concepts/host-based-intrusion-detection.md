A **host-based intrusion detection system (HIDS)** runs on the machine it protects and watches what happens *inside* it — the operating system's own record of who did what. It is one of the two deployments of an [[Intrusion Detection Systems|IDS]] in [[CSCE 465]]; the other is [[Network Intrusion Detection]], which watches the wire.

## What a HIDS Watches

> - **Using OS auditing mechanisms**
>   - E.g., **BSM on Solaris**: logs all direct or indirect events generated by a user
>   - **`strace`** for system calls made by a program
> - **Monitoring user activities**
>   - E.g., analyze shell commands
> - **Monitoring executions of system programs**
>   - E.g., analyze system calls made by `sendmail`

Three sources of evidence, from coarse to fine: the audit log, what users type, and what programs ask the kernel to do. The last is the one the lecture develops.

## A Sense of Self

The lecture's example HIDS is subtitled *Immunology Approach*:

> **Prof. Forrest at University of New Mexico**
> - Anomaly detection
> - Simple and **short sequences of events** to distinguish **"self" from not**
> - Currently looking at **system calls** (`strace`)
> - Apply to detection of `lpr` and `sendmail`

The analogy is with an immune system, which does not carry a catalogue of every pathogen. It knows what the body's own cells look like and reacts to whatever is not that. This is [[Misuse and Anomaly Detection|anomaly detection]] in its purest form: the model is of the program, not of any attack.

## The Mechanism

> **Anomaly detection for Unix processes** — "short sequences" of system calls as normal profile (Forrest et al., UNM)

```
trace of a running program:

    ..., open, read, mmap, mmap, open, getrlimit, mmap, close, ...

                |   sliding window of length k
                v

        open,  read,  mmap,  mmap
        read,  mmap,  mmap,  open
        mmap,  mmap,  open,  getrlimit
        mmap,  open,  getrlimit,  mmap
        ...

                |
                v
        % matched > ε ?  ---- Y ---->  normal
                         ---- N ---->  abnormal
```

A window of *k* consecutive system calls slides along the trace one call at a time. (The slide writes *k* without a value; each window it lists holds four calls.) The set of windows seen while the program runs normally is its **normal profile**. Afterwards, a running copy of the program is judged by the fraction of its windows that appear in that profile: above the threshold ε it is normal, below it abnormal.

> **Verified during ingest.** The trace on the slide has eight calls, which gives five windows of length 4. The slide lists the first four, and they are exactly the first four in order.

> **Why sequences and not just the set of calls, derived.** A compromised `sendmail` still calls `open` and `read`; every individual call is one the program legitimately makes. What changes when control is hijacked is the **order**. Injected code — the [[Shellcode|shellcode]] delivered by a [[Stack Smashing|stack smash]], say, whose whole purpose is to reach an `execve` — issues calls in a sequence the program's own code never produces. A short window is enough to see that, and short windows are cheap to store and compare.
>
> **Two knobs.** *k* sets how much context counts as a pattern, and ε is a threshold. Moving ε trades missed attacks against false alarms, so one such detector traces out one curve on the ROC plot in [[IDS Performance Metrics]]. And like every anomaly detector it has the weakness the lecture states for the class: a legitimate code path that never ran during training looks like an intrusion.

## Why the System-Call Interface

[[System Calls]] from [[CSCE 313]] is the mechanism: a system call is the only way a user-space process gets anything done outside its own memory — files, processes, the network. So the trace of system calls is a complete record of a program's effects on the world, taken at the one boundary it cannot go around. `strace` is the tool that prints that trace, and the calls on the slide (`open`, `read`, `mmap`, `close`) are the file and memory calls from that page.

## Host and Network Compared

| | Host-based | [[Network Intrusion Detection\|Network-based]] |
|---|---|---|
| Watches | OS audit records, shell commands, system calls | Packets |
| Lecture's tools | BSM, `strace` | `tcpdump`, libpcap |
| Encryption | Sees activity after decryption, on the host | *May be easily defeated by encryption* |
| What it reconstructs | Nothing — it observes the real execution | What the end host *probably* received |
| Coverage | One machine per installation | Every host behind the sensor |

> **Derived from the two slides.** The rows marked for encryption and reconstruction are the reason both kinds exist. A network IDS has to *guess* what a packet stream will mean to the host that receives it, and can be fooled about it ([[Insertion and Evasion Attacks]]). A host IDS does not guess; it is watching the program run. The price is that it lives on the machine being attacked, so an intruder who gains enough privilege can turn it off or rewrite its log — the point [[Security Policy and Mechanism]] made in Lecture 2, that detection depends on an audit trail something else must protect.
